# Rendered playthrough verification

Run `python tests/run_playthrough.py` from the project directory with Godot and a working graphical display available. The runner copies the current assets, scripts, scenes and tests into a fresh `/tmp/justlife-playthrough-*` directory. It strips editor plugins, MCP toolkit configuration and autoloads, and sets separate XDG data/config/cache directories. It never starts the working project's editor or registers an MCP runtime. The GDScript harness refuses to run outside this isolated path.

Import uses headless editor mode; both gameplay processes use the actual project renderer and a 1440 × 900 window. Screenshots come from the rendered viewport after a draw, rather than from synthetic scene reconstructions. The temporary path, logs and evidence location are printed by the runner. Source hashes accompany every snapshot.

The first process creates two distinct Lifelets through creator controls and household chips; chooses a home; queues cooking, showering and conversation for the first alongside reading for the second; observes real routing, gradual effects, charges and separate skill gains; tests pause and an eight-action queue; buys a furnishing with actual mouse events; rejects an overlapping placement; draws a room and doorway; rejects overlapping construction; sits and sleeps. It then saves during a nonzero-cost cooking action and reloads. The second process compares both household members and world state, resumes the charged cooking action without another charge, and lets both Lifelets act autonomously until the following morning.

Button actions emit the production button signal. This exercises the connected UI callback, including signal-time lifecycle errors; it is not an exhaustive test of physical pointer hit targets. Furnishing and construction placement use input mouse events and desktop pointer warping. A minimal Godot experiment confirmed that synthetic motion alone does not change the position returned by `Viewport.get_mouse_position()`, which the placement preview reads. The harness never teleports the actor, calls simulation tick directly, or pretends an action has arrived. It temporarily pauses and changes camera framing for activity evidence.

The runner fails on failed assertions, missing result files, engine/script error lines, nonzero exits or timeout. Passing state comparisons alone do not establish a usable screen: the critic also inspects the captured creator, live, active-object, full-queue, build and resume images. A supported smaller window, prolonged multi-day progression, all activity types, audio and every household composition still require additional verification.

Results are snapshot-specific. A passing run does not verify changes made to the shared project after that snapshot was copied. Preserve failed evidence with its source hashes, then repeat only when code changes or a justified test correction warrants it.

Latest reviewed checkpoint: 8 September 2026, `art/screenshots/playthrough_iteration_02/`. Both processes passed with 164 and 30 assertions, zero engine/script error lines, and 22 rendered captures. The household continued to Day 2 at 08:00. This result applies to the source hashes preserved beside the screenshots; the evolving shared project may be newer.
