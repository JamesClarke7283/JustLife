# Named household saves

`LifeSaveLibrary` is a static backend in `scripts/save_library.gd`. It derives every filename from a slot ID, keeps managed saves in `~/.justlife/saves` (Windows: `%USERPROFILE%\.justlife\saves`), and validates the household through `LifeHousehold.restore_state()` before saving or returning loaded data. `scripts/save_storage.gd` resolves the storage root and imports older saves. An absolute `JUSTLIFE_DATA_DIR` overrides the root; the `saves` subfolder is appended once. An explicitly empty or relative override is an error.

- `save_slot(id, name, state, preview: Image = null) -> Dictionary`: returns `{ok: true, id}` or `{ok: false, error}`. Empty ID creates a new slot; an existing ID overwrites that exact slot. Names are display text, limited to sixty characters. A successful save may include an optional `warning` if its display metadata or preview could not be updated.
- `list_saves() -> Array`: newest first, with `{id, name, saved_at, day, minutes, members, preview_path, valid, error}`. `saved_at` is an ISO UTC string. `members` contains Lifelet names. `preview_path` is a derived absolute PNG path or an empty string. Corrupt saves remain listed with `valid: false`, so the UI can offer deletion while disabling load. Invalid optional metadata falls back to validated household details.
- `storage_error() -> String`: explains an unavailable storage root or interrupted import. The picker displays this distinctly from an empty library.
- `read_slot(id) -> Dictionary`: returns `{ok: true, data}` or `{ok: false, error}`. The controller passes `data` to its own `household.restore_state()` and restores world state from the result. Reading does not replace any live household.
- `latest_id() -> String`: returns the newest readable slot ID, or an empty string.
- `delete_slot(id) -> Dictionary`: removes that exact slot and its own fixed preview/temporary files, returning `{ok}` and an error on failure. The UI owns the user's confirmation step.

IDs are lowercase ASCII letters, digits, underscores or hyphens, at most sixty-four characters, beginning with a letter or digit. Traversal paths, separators, uppercase and empty read/delete IDs are rejected. Symbolic save directories and symbolic save files are rejected. Preview paths from metadata are ignored.

The managed JSON file contains `{save_library_version: 1, metadata, data}`. Household data is written to a temporary file, flushed, then atomically renamed over its destination. Files larger than eight MiB are rejected before reading/parsing or writing. Optional previews are resized to fit 640 × 640 and saved separately; preview failure does not undo a successful household save.

The fixed legacy `<root>/justlife_save.json` appears as slot `legacy` when present. It can be read, overwritten and deleted through the same API. Its household JSON remains in the older raw format; optional display metadata is stored in `<root>/saves/legacy.metadata.json`. The simulator-only `LifeHousehold.load_game()` compatibility method still reads its original `user://` path; the game's menus use `LifeSaveLibrary`.

On first use, a `save_import.json` journal reserves destinations before copying old `user://saves` entries and the raw legacy file. Originals and previews are copied without changing their bytes. Name collisions receive distinct imported IDs; a colliding valid legacy payload is embedded verbatim inside a named envelope. Interrupted imports resume only when source hashes and already-copied destinations match. Linked paths and changed destinations stop import without overwriting saves. A completed journal prevents deleted imports from reappearing. This does not provide simultaneous-writer transaction isolation.

Household validation enforces canonical member IDs (`player`, then `housemate_1` through `housemate_7`), matching housemate relationship names, no self relationships, finite integer selection, and consistent shared wallet/clock/speed. Malformed data is rejected before the live household changes. Legacy single-Lifelet migration removes stale housemate references.

`python tests/run_save_storage.py` runs 138 backend and path checks in isolated directories and fresh processes, including the existing save-library suite. It covers collision preservation, interrupted imports, exact legacy numbers, deletion across restart, malformed data and linked paths. The runner currently requires Linux; Windows path syntax has lexical coverage only. Other game tests must set both private `XDG_DATA_HOME` and `JUSTLIFE_DATA_DIR` before instantiating the main scene. The release probe rejects incomplete isolation before opening the menu. Never point test overrides at player saves.
